# 4.3(a) 拒审差异化改造计划

> 状态：方案（待确认后执行代码改动）
> 关联：App Store 拒审 Guideline 4.3(a) - Spam
> 确认事实：`knot_phone` **未**提交过 App Store，本次只提交了 `tool_box`。

---

## 1. 诊断结论（已修正）

- **不是**「同开发者多款相似 app」的 spam（knot_phone 没提过，无 sibling-app 冲突）。
- **是** 4.3(a) 的另一半——**「通用模板 / 缺乏独特功能」**（`well-established app concepts
  without unique features`）。
- **无账号级 spam 风险**，可通过"真差异化"修复，不必走对抗式申诉。
- **真实触发点**：compass / ruler / level / tide / noise / world_clock / unit_converter /
  memo 全是商品化通用件，组合成一个"工具箱"模板样貌；真正独有的只有
  `rope_length_calculator`（绳长计算器，含 6 种绳结系数 + 缠绕/按结两种算法）。

> 反例佐证：`pubspec.yaml` 第 2 行自述"复刻 knot_phone 工程架构…的独立工具应用"，
> 以及历史记录里"tool_box 是 knot_phone 的子集"——这些若被审核员看到会**加重模板观感**，
> 必须在改造中一并抹掉。

## 3. 推荐定位（从"工具箱"→"绳结/绳索工具"）

把 app 的核心身份从泛化"户外工具箱"收束到 **绳结/绳索专用领域**：

- **概念**：为户外、航海、攀岩、救援、捆扎场景的绳结使用者，提供
  "该用多长绳、怎么受力、怎么选结"的**专用计算与参考工具**。
- **名称建议（App Store Connect 侧，非代码中英混排）**：避免 "Toolbox / 工具箱 / 多功能"
  这类泛词；用带领域词的，例如 `KnotLab 绳结助手` / `RopeCalc 绳索计算` / `绳匠 Knotsmith`。
- **核心三件套**：
  1. 绳长计算器（已有，扩展更多系数 + 参考库）
  2. 受力/安全载荷换算（已有 force_converter，强化）
  3. 绳结参考库（**新增**）：每个结的用途、强度、最少绳长、安全提示——把现有 6 个系数
     扩展成可视化内容页，形成"内容 + 功能"组合（最难被判为模板）。

---

## 4. 需新增的"独特内容"（让审核员看到真东西）

- **绳结参考库**：基于现有 `_knotRules`（overhand / figure8 / reef / clove_hitch /
  sheet_bend / double_fisherman）扩展为**内容页**——图示/用途/最少绳长/安全提示。
- **多绳种支持**：不同直径、材质（尼龙/涤纶/麻）的绳长修正系数。
- **场景化**：航海缆绳、攀岩动力绳、救援静力绳各自的推荐参数预设。

这些是把"通用计算器"升级为"领域专用工具"的关键增量。

## 6. App Store Connect 元数据（**同样关键**）

4.3(a) 文本点名了 **"metadata"**，光改 app 不够，提交信息也要改：

- **名称 / 副标题 / 描述 / 关键词**：全改成绳结/绳索领域，
  **不能再出现**"工具箱 / 实用工具 / 多功能 / 日常必备"等泛词。
- **截图主图**：必须是 `rope_length_calculator`、绳结参考库这类**独特功能**；
  **不要用**指南针/尺子/水平仪的截图（强化模板观感）。
- **描述开头**：讲清"为谁、解决什么绳结场景问题"，而非罗列通用工具清单。

---

## 7. 申诉 vs 重提？

- **更建议：重做定位后重新提交（resubmit）**，而非硬申诉。
  原因：当前功能面确实偏通用，申诉胜算低；差异化改造后自然合规、最稳。
- 若坚持申诉：须在回复里逐条解释每个功能的绳结领域关联性——
  但通用件太多会显得牵强，不推荐。
